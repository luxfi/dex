# Sidecar Architecture

The LX DEX runs as a standalone sidecar daemon (`lxd`) separate from the Lux blockchain node. This architecture enables sub-millisecond order matching while maintaining blockchain settlement guarantees through Warp messaging.

## Design Rationale

### Why a Sidecar?

Traditional DEX architectures embed trading logic directly in blockchain VMs. This creates fundamental performance limitations:

| Approach | Latency | Throughput | Trade-off |
|----------|---------|------------|-----------|
| On-chain VM | 2-30s | 100-1000 TPS | Guaranteed finality, slow |
| Hybrid | 100ms-2s | 10K TPS | Compromise |
| **Sidecar** | `<100μs` | 10M+ TPS | Fast matching, async settlement |

The sidecar approach separates concerns:

1. **Matching**: Handled in `lxd` with native performance
2. **Settlement**: Committed to blockchain via Warp messages
3. **Consensus**: DAG consensus within sidecar network

```
+=====================================+
|          SIDECAR NETWORK            |
|  +------+   +------+   +------+     |
|  | lxd  |<->| lxd  |<->| lxd  |     |
|  +------+   +------+   +------+     |
|      |          |          |        |
|      +----+-----+-----+----+        |
|           |           |             |
|      DAG Consensus    |             |
|           |           |             |
+===========|===========|=============+
            |           |
       Warp Messages    |
            |           |
+===========v===========v=============+
|        LUX BLOCKCHAIN NODE          |
|  +--------+  +--------+  +-------+  |
|  | D-Chain|  | C-Chain|  |B-Chain|  |
|  +--------+  +--------+  +-------+  |
+=====================================+
```


```
3. NETWORK SETUP
```

## Trading Engine Integration

### Order Processing Pipeline

```go
// OrderProcessor handles the full order lifecycle
type OrderProcessor struct {
    engine   *TradingEngine
    dag      *DAGConsensus
    warp     *WarpClient
    metrics  *Metrics
}

// ProcessOrder handles a new order from gateway
func (p *OrderProcessor) ProcessOrder(ctx context.Context, req *OrderRequest) (*OrderResponse, error) {
    // 1. Validate order
    order, err := p.validateOrder(req)
    if err != nil {
        return nil, fmt.Errorf("validation failed: %w", err)
    }

    // 2. Risk check
    if err := p.riskCheck(ctx, order); err != nil {
        return nil, fmt.Errorf("risk check failed: %w", err)
    }

    // 3. Add to order book
    orderID := p.engine.OrderBooks[order.Symbol].AddOrder(order)
    if orderID == 0 {
        return nil, ErrOrderRejected
    }

    // 4. Create DAG vertex (async)
    go p.createVertex(ctx, order)

    // 5. Return immediately
    return &OrderResponse{
        OrderID:   orderID,
        Status:    "accepted",
        Timestamp: time.Now(),
    }, nil
}

// createVertex creates a DAG vertex for consensus
func (p *OrderProcessor) createVertex(ctx context.Context, order *Order) {
    vertex := &OrderVertex{
        ID:        generateVertexID(order),
        Order:     order,
        NodeID:    p.dag.NodeID(),
        Height:    p.dag.Height(),
        Parents:   p.dag.Frontier(),
        Timestamp: time.Now(),
    }

    // Add to local DAG
    p.dag.AddVertex(vertex)

    // Broadcast to peers
    p.dag.BroadcastVertex(ctx, vertex)
}
```

**Worker Pool Design:**

```go
type WorkerPool struct {
    workers    int
    orderChan  chan *Order
    resultChan chan *OrderResult
    wg         sync.WaitGroup
}

func NewWorkerPool(size int) *WorkerPool {
    pool := &WorkerPool{
        workers:    size,
        orderChan:  make(chan *Order, 10000),
        resultChan: make(chan *OrderResult, 10000),
    }

    for i := 0; i < size; i++ {
        pool.wg.Add(1)
        go pool.worker(i)
    }

    return pool
}

func (p *WorkerPool) worker(id int) {
    defer p.wg.Done()

    // Pin to CPU core for cache locality
    runtime.LockOSThread()

    for order := range p.orderChan {
        result := p.processOrder(order)
        p.resultChan <- result
    }
}
```

## Warp Messaging

### Message Types

The sidecar uses Warp messages to communicate with the blockchain:

```go
// WarpMessageType defines the type of Warp message
type WarpMessageType uint8

const (
    WarpSettlement     WarpMessageType = iota + 1  // Trade settlement
    WarpWithdrawal                                 // Asset withdrawal
    WarpDeposit                                    // Asset deposit
    WarpLiquidation                                // Position liquidation
    WarpStateSync                                  // State synchronization
)

// WarpMessage represents a message to the blockchain
type WarpMessage struct {
    Type        WarpMessageType
    Payload     []byte
    Signature   []byte           // BLS signature
    RTSignature []byte           // Corona (post-quantum)
    Timestamp   time.Time
    SourceChain [32]byte
    DestChain   [32]byte
}
```

### Settlement Flow

```
SIDECAR                           BLOCKCHAIN
   |                                  |
   |  1. Trade executed locally       |
   |                                  |
   |  2. Create settlement batch      |
   |                                  |
   |  3. Generate Warp message        |
   |                                  |
   |  4. Collect validator sigs       |
```

### Warp Client Implementation

```go
// WarpClient handles blockchain communication
type WarpClient struct {
    nodeRPC      string
    chainID      [32]byte
    signer       *BLSSigner
    rtSigner     *CoronaSigner
    pendingBatch []*Settlement
    batchMu      sync.Mutex
    flushTicker  *time.Ticker
}

// Settlement represents a trade settlement
type Settlement struct {
    TradeID     uint64
    BuyerAddr   [20]byte
    SellerAddr  [20]byte
    BaseAsset   [32]byte
    QuoteAsset  [32]byte
    BaseAmount  *big.Int
    QuoteAmount *big.Int
    Timestamp   time.Time
}

// BatchAndSend collects settlements and sends as Warp message
func (c *WarpClient) BatchAndSend(ctx context.Context) error {
    c.batchMu.Lock()
    batch := c.pendingBatch
    c.pendingBatch = make([]*Settlement, 0, 1000)
    c.batchMu.Unlock()

    if len(batch) == 0 {
        return nil
    }

    // Encode batch
    payload, err := encodeSettlementBatch(batch)
    if err != nil {
        return fmt.Errorf("encode batch: %w", err)
    }

    // Create unsigned message
    unsignedMsg := &warp.UnsignedMessage{
        NetworkID:     c.networkID,
        SourceChainID: c.chainID[:],
        Payload:       payload,
    }

    // Sign with BLS
    blsSig, err := c.signer.Sign(unsignedMsg.Bytes())
    if err != nil {
        return fmt.Errorf("BLS sign: %w", err)
    }

    // Sign with Corona (post-quantum)
    rtSig, err := c.rtSigner.Sign(unsignedMsg.Bytes())
    if err != nil {
        return fmt.Errorf("Corona sign: %w", err)
    }

    // Send to blockchain
    msg := &WarpMessage{
        Type:        WarpSettlement,
        Payload:     payload,
        Signature:   blsSig,
        RTSignature: rtSig,
        Timestamp:   time.Now(),
        SourceChain: c.chainID,
    }

    return c.sendToBlockchain(ctx, msg)
}
```

## State Synchronization

### Initial Sync

When a new sidecar joins the network:

```go
// StateSyncer handles state synchronization
type StateSyncer struct {
    peers    []string
    dag      *DAGConsensus
    engine   *TradingEngine
}

// SyncFromPeers synchronizes state from peer sidecars
func (s *StateSyncer) SyncFromPeers(ctx context.Context) error {
    // 1. Get latest height from peers
    heights := make(map[string]uint64)
    for _, peer := range s.peers {
        h, err := s.getHeight(ctx, peer)
        if err != nil {
            continue
        }
        heights[peer] = h
    }

    // 2. Find peer with highest height
    bestPeer, bestHeight := s.selectBestPeer(heights)

    // 3. Download state snapshot
    snapshot, err := s.downloadSnapshot(ctx, bestPeer, bestHeight)
    if err != nil {
        return fmt.Errorf("download snapshot: %w", err)
    }

    // 4. Verify snapshot integrity
    if err := s.verifySnapshot(snapshot); err != nil {
        return fmt.Errorf("verify snapshot: %w", err)
    }

    // 5. Apply snapshot
    if err := s.applySnapshot(snapshot); err != nil {
        return fmt.Errorf("apply snapshot: %w", err)
    }

    // 6. Sync remaining blocks
    return s.syncBlocks(ctx, bestPeer, snapshot.Height, bestHeight)
}

// StateSnapshot represents a point-in-time state
type StateSnapshot struct {
    Height     uint64
    Timestamp  time.Time
    OrderBooks map[string]*OrderBookState
    DAGState   *DAGState
    Checksum   [32]byte
}
```

### Continuous Sync

```go
// ContinuousSync maintains state consistency
func (s *StateSyncer) ContinuousSync(ctx context.Context) error {
    ticker := time.NewTicker(100 * time.Millisecond)
    defer ticker.Stop()

    for {
        select {
        case <-ctx.Done():
            return ctx.Err()

        case <-ticker.C:
            // Check for new vertices from peers
            for _, peer := range s.peers {
                vertices, err := s.getNewVertices(ctx, peer)
                if err != nil {
                    continue
                }

                for _, v := range vertices {
                    if err := s.dag.ProcessRemoteVertex(v); err != nil {
                        log.Warn("process vertex", "err", err)
                    }
                }
            }
        }
    }
}
```

## Fault Tolerance

### Health Checking

```go
// HealthChecker monitors system health
type HealthChecker struct {
    components map[string]HealthCheckable
    interval   time.Duration
}

// HealthCheckable interface for health checking
type HealthCheckable interface {
    HealthCheck(ctx context.Context) error
    Name() string
}

// Check performs health check on all components
func (h *HealthChecker) Check(ctx context.Context) *HealthReport {
    report := &HealthReport{
        Timestamp: time.Now(),
        Status:    "healthy",
        Components: make(map[string]*ComponentHealth),
    }

    for name, component := range h.components {
        start := time.Now()
        err := component.HealthCheck(ctx)
        latency := time.Since(start)

        health := &ComponentHealth{
            Name:    name,
            Latency: latency,
        }

        if err != nil {
            health.Status = "unhealthy"
            health.Error = err.Error()
            report.Status = "degraded"
        } else {
            health.Status = "healthy"
        }

        report.Components[name] = health
    }

    return report
}
```

### Graceful Shutdown

```go
// Shutdown gracefully stops the daemon
func (d *Daemon) Shutdown(ctx context.Context) error {
    log.Info("initiating graceful shutdown")

    // 1. Stop accepting new orders
    d.gateway.StopAccepting()

    // 2. Drain pending orders
    drainCtx, cancel := context.WithTimeout(ctx, 30*time.Second)
    defer cancel()

    if err := d.engine.DrainOrders(drainCtx); err != nil {
        log.Warn("drain orders timeout", "err", err)
    }

    // 3. Flush pending settlements
    if err := d.warpClient.FlushBatch(ctx); err != nil {
        log.Error("flush settlements", "err", err)
    }

    // 4. Save state checkpoint
    if err := d.saveCheckpoint(); err != nil {
        log.Error("save checkpoint", "err", err)
    }

    // 5. Close connections
    d.gateway.Close()
    d.consensus.Stop()

    // 6. Cancel context
    d.cancel()
    d.wg.Wait()

    log.Info("shutdown complete")
    return nil
}
```

## Trade-offs and Design Decisions

### ADR-001: Sidecar vs On-Chain Matching

**Context**: Need to achieve &lt;100us order latency while maintaining settlement guarantees.

**Decision**: Run matching engine as standalone sidecar, settle via Warp messages.

**Trade-off**:
- **Pro**: Sub-millisecond latency, 10M+ TPS
- **Pro**: Horizontal scalability via sharding
- **Con**: Additional operational complexity
- **Con**: Async settlement (eventual consistency)

**Rationale**: The latency and throughput requirements are impossible to meet on-chain. The sidecar approach provides native performance while Warp messaging ensures eventual settlement finality.

### ADR-002: DAG Consensus for Order Sequencing

**Context**: Need to establish total ordering of trades across distributed sidecars.

**Decision**: Use DAG consensus with Lux FPC protocol.

**Trade-off**:
- **Pro**: 50ms finality
- **Pro**: Parallel vertex processing
- **Con**: More complex than linear blockchain
- **Con**: Requires quantum certificates for finality

**Rationale**: DAG enables parallel processing of non-conflicting orders, significantly increasing throughput compared to sequential consensus.
